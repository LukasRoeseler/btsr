      Programmierschule

      Zieh die Punkte in den beiden Kurven nach oben oder unten. Links legst du fest, wie stark das Auto über die Zeit Gas gibt oder bremst, rechts wie es lenkt. Dann Simulation fahren — und darunter siehst du, was das Auto daraus macht.

      Das ist der ganze Trick: eine eckige Vorgabe führt nicht zu einer eckigen Bewegung. Das Auto hat Masse, die Reifen brauchen Zeit, die Lenkung hat eine Höchstgeschwindigkeit. Wer das einmal gesehen hat, versteht, warum geschmeidige Vorgaben besser fahren — und das gilt für Programme genauso wie für Daumen.

      Noch nicht gefahren.

      Oben = Vollgas, Mitte = rollen, unten = Vollbremse.

      Wozu dient dieses Projekt?

      Die Hardware ist gekauft, die Software bestimmt jemand anders. Dieses Projekt dreht das um: es steuert ein Carrera-Hybrid-Auto mit eigenem Code über dieselbe Bluetooth-Schnittstelle, die die Hersteller-App benutzt. Damit läuft auf der Hardware, was man selbst darauf laufen lassen will — unabhängig davon, ob ein Anbieter eine Funktion vorsieht, eine App weiter pflegt oder einen Server abschaltet.

      Der zweite Punkt ist die Gemeinschaft. Ein offengelegtes Protokoll kann jeder weiterverwenden: für Funktionen, die der Hersteller nicht baut, für eine andere Bedienung, für Unterricht. Das hier ist bewusst als Beispiel gebaut, nicht als Produkt — alles, was herausgefunden wurde, steht in dieser Doku, samt der Stellen, an denen wir uns geirrt haben.

      Offene Software als Teil offener Wissenschaft

      Wer Ergebnisse prüfbar machen will, braucht prüfbare Werkzeuge. Eine Auswertung, die auf einem Programm beruht, in das niemand hineinsehen darf, ist genau so weit nachvollziehbar wie das Vertrauen in dessen Hersteller reicht. Deshalb wechseln Forschende zunehmend von kommerzieller auf offene Software, und deshalb steigen auch Landesverwaltungen von Windows auf Linux um — es geht um Kontrolle über die eigene Infrastruktur, nicht um Anschaffungskosten.

      Offene Software kann dabei sogar sicherer sein, und der Grund dafür ist Kerckhoffs’ Prinzip: ein Verfahren soll seine Sicherheit aus dem geheimen Schlüssel ziehen, nicht aus der Geheimhaltung des Verfahrens. Ein Verfahren, das nur funktioniert, solange niemand es kennt, ist nicht sicher, sondern unprüfbar. Offenlegung ist deshalb kein Risiko, sondern die Voraussetzung dafür, dass Fehler gefunden werden können. Das heißt nicht, dass offene Software automatisch sicherer ist — nur, dass Prüfbarkeit und Sicherheit sich nicht widersprechen.

      Ada & Zangemann von Matthias Kirschner und Sandra Brandstätter — ein Kinderbuch darüber, wem die Software auf einem Gerät eigentlich gehört. Es erklärt in einer Geschichte, worum es oben in drei Absätzen ging.

      Überblick

      Carrera Hybrid mischt klassische Carrera-Rennbahn mit freiem Ferngesteuert-Fahren. Auf einer klassischen Bahn läuft das Auto in einer Schienenrille und kann nicht abkommen. Bei Carrera Hybrid fahren die Fahrzeuge frei, ohne Schiene. Die Streckenteile tragen eine Markierung, die ein Sensor im Auto liest, damit das Auto trotzdem weiß, wo es ist.

      Gesteuert wird per Smartphone-App über Bluetooth, optional mit einem Controller-Aufsatz für das Handy.

      Hardware — Auto und Strecke

      Der Aufbau des Autos

      • Motor: treibt die Hinterräder an.
      • Lenkservo: dreht die Vorderräder.
      • Akku: wiederaufladbar, im Fahrzeug.
      • Bluetooth-Chip: hält die Verbindung zum Handy. Vermutlich Nordic nRF52.
      • Sensor: liest die Streckenmarkierung. Kamera oder Infrarot ist nicht sicher bekannt.
      • Lichter: mindestens Frontscheinwerfer. Ein Bremslicht ist nicht bestätigt.

      Wie das Auto auf Gas und Lenkung reagiert, berechnet das Auto selbst. Die App schickt nur Zielwerte.

      Streckenteile und Streckenscan

      Jedes Streckenteil (Gerade, Kurve, Start-Ziel) trägt ein eigenes, für Menschen kaum sichtbares Muster. So erkennt das Auto den Teiltyp und ob es noch auf der Strecke ist. Die Teile liegen lose, also kann jede Strecke frei gebaut werden, und das Auto darf sie auch komplett verlassen.

      Vor einem Rennen kann die App die Strecke einmal abscannen: Das Auto fährt sie ab, meldet jedes neu erkannte Teil per Bluetooth, und daraus entsteht Stück für Stück eine digitale Streckenkarte.

      Der Barcode auf der Bahn

      Jedes Streckenteil trägt ein gedrucktes Muster, das das Auto beim Überfahren liest und als Zahl meldet (Byte 12 der Statusmeldung). Das Muster ist ein Strichcode aus Balken und Lücken, quer über die ganze Fahrbahn — und genau weil er quer über die ganze Breite läuft, liest er sich an jeder Querposition gleich. Das ist der Grund, warum in diesem Code grundsätzlich keine Information darüber steckt, wo auf der Bahn das Auto fährt.

      Lang und kurz, nicht hell und dunkel

      Kodiert wird über die Breite der Elemente, in zwei Stufen. Aus der Original-Druckvorlage für Start/Ziel exakt ausgemessen (Vektordatei, deshalb auf Hundertstelmillimeter):

      ElementschmalbreitVerhältnis
      Balken3,598 mm6,604 mm1 : 1,84
      Lücke3,514 mm6,520 mm1 : 1,86

      Balken und Lücken tragen beide Information. Das ist leicht zu übersehen — eine frühere Rekonstruktion dieses Blattes hat nur die Lückenfolge nachgebildet und war deshalb unbrauchbar, obwohl sie auf dem Papier richtig aussah.

      Das Beispiel Start/Ziel

      Neun Balken, acht Lücken, zusammen 17 Elemente. In Leserichtung, mit 0 = schmal und 1 = breit:

      Balken  0 0 0 0 1 0 0 1 0
      Lücken    0 0 0 1 0 1 1 0

      Das ganze Muster ist 75,5 mm lang in Fahrtrichtung, die Balken sind 275,9 mm breit — also fast die volle A4-Breite quer zur Fahrbahn. Erzeugt wird das Blatt von tools/make_pattern.py direkt aus der Original-PDF, damit keine Zahl abgeschrieben wird; die größte Abweichung zum Original beträgt 0,0004 mm.

      Warum die Richtung zählt

      Ein Strichcode ist eine Folge, und eine Folge rückwärts gelesen ist eine andere Folge. 0 0 0 0 1 0 0 1 0 von hinten ist 0 1 0 0 1 0 0 0 0 — ein anderes Muster, also ein anderer Code oder gar keiner. Deshalb trägt die Druckvorlage einen Richtungspfeil, und deshalb muss das Blatt richtig herum ausgelegt werden. Beim Ausdrucken gilt dasselbe für den Maßstab: „an Seite anpassen“ verkleinert um mehrere Prozent und macht das Muster unlesbar, weshalb auf dem Blatt eine 100-mm-Maßstabsprobe mitgedruckt wird.

      Was wir nicht wissen

      Die belegten Codes sind 0x01 Start/Ziel, 0x02 Gerade, 0x03 Linkskurve, 0x04 Rechtskurve und 0x00 abseits der Bahn. Die Kodierungsregel selbst kennen wir nicht. Aus einem exakt ausgemessenen Muster lässt sich nicht ableiten, wie die 17 Elemente in die Zahl 0x01 übersetzt werden — dafür bräuchte es die Muster der anderen Kacheln, senkrecht von oben fotografiert und mit Maßstab. Bis dahin gilt: wir können Start/Ziel exakt reproduzieren, aber kein neues Muster erfinden.

      Protokoll — was über Bluetooth läuft

      Die Bluetooth-Verbindung

      Handy und Auto sprechen über Bluetooth Low Energy (BLE), den stromsparenden Standard, den auch Kopfhörer oder Fitness-Tracker nutzen. Der Kanal heißt Nordic UART Service, eine Art virtuelle serielle Leitung über Bluetooth, die viele kleine Elektronikgeräte verwenden.

      Die App schickt nicht nur einmal ein Kommando: Sie sendet etwa 20 bis 45 Mal pro Sekunde den aktuellen Gas- und Lenkwert. Bleibt dieser Strom aus, geht das Auto vermutlich in einen sicheren Stillstand über. In die andere Richtung meldet das Auto laufend Statuspakete: Akkustand, erkanntes Streckenteil, Off-Track-Status und rohe Bewegungssensordaten.

      Ein einziger Schreiber

      Alle Bluetooth-Schreibvorgänge laufen über einen Takt von 45 ms mit einer Sperre, die immer nur einen Schreibvorgang gleichzeitig zulässt. Das ist keine Stilfrage: vorher schrieben fünf Quellen unabhängig voneinander — Gamepad, Tastatur, Zeigegerät, Neigungssensor und die Fahrphysik. Überlappende Schreibvorgänge quittiert der Browser mit „GATT operation already in progress“, verwirft sie stillschweigend, und das Auto ruckelt.

      Praktische Folge für Weiterentwicklungen: eine neue Funktion darf niemals selbst senden. Sie setzt einen Zustand, den der Takt beim nächsten Paket mitnimmt. Die Lichtsteuerung ist dafür das Musterbeispiel — sie schreibt kein eigenes Paket, sie setzt Byte 14.

      Ebenso gibt es eine Eingabeschlichtung: jede Quelle meldet sich pro Achse an und darf nur schreiben, solange sie ausgelenkt ist, plus genau einmal beim Loslassen. Sonst überschreibt ein mit 60 Hz laufendes Gamepad ständig die Tastatur mit Nullen.

      Mehrere Autos, Ghosts, Mustererkennung

      Garage und Rollen

      Jedes Auto braucht eine eigene Nutzergeste zum Verbinden — Web Bluetooth verlangt das je requestDevice(), das ist nicht umgehbar. Klick auf eine Zeile lässt die Lichter dieses Autos blinken (Byte 14 wechselweise 0x82/0x80), damit Liste und Tisch zuzuordnen sind.

      Die Architektur ist absichtlich unsymmetrisch. Das Spielerauto behält den bestehenden Pfad vollständig: sendControlValue(), den einen 45-ms-Takt, Optionen, HUD. Dieser Zustand steckt in etwa 20 Modulvariablen mit über hundert Verwendungen; ein Umbau auf ein Fahrzeugobjekt hätte jede davon angefasst. Ghosts sind stattdessen Objekte mit eigener Verbindung, eigener Schreibsperre und eigener CarreraPhysicsEngine-Instanz. Letzteres erledigt „gleich stark beschleunigen wie das Spielerauto“ von selbst — gleiche Klasse, gleiche Kalibrierung — und bringt Gangschaltung, Byte-Herleitung und Bremslicht mit, statt sie nachzubauen.

      Wie ein Ghost fährt

      Byte 12 sagt Kurve, aber nicht in welche Richtung, und das Vorzeichen von Byte 3 hängt an der Fahrtrichtung über das Streckenteil. Ein falsch geratenes Vorzeichen lenkt den Ghost sofort von der Bahn. Die Richtung kommt deshalb aus dem Streckenlayout im Strecke-Tab, wo Links- und Rechtskurven unterschieden sind; Byte 11 sagt, auf welchem Teil man ist. Ohne Layout kann ein Ghost nur geradeaus halten und wird an der ersten Kurve von der Abschaltregel gestoppt. Das ist eine echte Grenze, kein Fehler.

      Mustercode entprellen

      Zwei Regeln gegen Fehllesungen. Erstens Bestätigung: ein Code muss zweimal hintereinander kommen, bevor er geglaubt wird. Das kostet ein Paket Latenz und nichts weiter — bei 8 bis 60 Paketen je Streckenteil ist eine echte Lesung nie ein Einzelpaket. Zweitens keine Sofortwiederholung: nach einem Start/Ziel- oder Boxengassen-Code wird derselbe Code für 1 s ignoriert. Vorher war der Teilzähler der einzige Schutz, und ein stotternder Zähler ergab Doppelrunden.

      Regen und Blitz auf dem Dash

      Bewusst CSS und kein Canvas: ein Canvas mit hunderten Tropfen bräuchte eine rAF-Schleife auf demselben Hauptthread, der alle 45 ms das Steuerpaket schreibt — dort sind die zwei schlimmsten Regressionen dieses Projekts entstanden. Drei Schichten mit translate3d laufen auf der GPU und kosten den Sendetakt nichts.

      Zwei Fehlversuche, und der Grund ist ein Einheitenfehler, kein Geschmacksfehler. repeating-linear-gradient malt Bänder über die ganze Fläche, also Streifen. Der zweite Versuch mit background-size: 1.6px 13px ergab wieder Streifen, weil background-size die Kachel bemisst und nicht den Tropfen: eine 1,6 px breite Kachel heißt ein Strich alle 1,6 px, rund 50 % der Fläche bemalt. Tropfen entstehen erst durch eine große Kachel mit einer kleinen Ellipse aus radial-gradient: 0,9×7 px in 24×46 px bemalt 1,8 % statt 50 %. Die drei Blätter bemalen 1,79 %, 1,18 % und 0,70 %. Die Drehung steht vor der Verschiebung, damit jeder Tropfen entlang seiner eigenen Längsachse fällt.

      Der Blitz ist echtes Gamma (feComponentTransfer type="gamma"), nicht brightness(): eine Multiplikation brennt die Lichter aus, Gamma hebt die Mitten und lässt Schwarz schwarz — das sieht nach kurzem Fremdlicht aus statt nach Weißblitz. Zwei Blitze, der zweite schwächer, dann der Donner 200 ms später. Der Blitz hängt am Wetter, nicht an der Lautstärke: eine stumme Ambience darf kein unsichtbares Gewitter ergeben.

      Eine verlorene Formatierung

      Ehrlichkeitsvermerk, weil es erklärt, warum das Optionsmenü längere Zeit unbrauchbar aussah: Commit 7cd71e6 hat einen CSS-Block zwischen zwei Markern ersetzt und dabei die Regeln für .opt-row, .opt-label, .opt-val und .tgl mitgelöscht. Markup und JavaScript blieben, deshalb liefen alle Funktionstests weiter durch, während der Tab gar keine Formatierung hatte — ohne Zeilenraster stapeln sich Beschriftung und Bedienelement einfach untereinander. Lehre: Tests, die nur Verhalten prüfen, bemerken verlorene Darstellung nicht.

      Autonome Autos: was die Original-App wirklich sendet

      Zwei Mitschnitte tragen das hier. Der vom 20.08. zeigt den Leitplanken-Modus (67 s Verkehr zum Auto; die 2755 s Dateispanne gehören zum gesamten Bluetooth-Verkehr des Telefons). Der vom 21.08. ist ein Rennen auf „az2108“ mit drei Autos: einem gesteuerten, das wegen eines nicht verbundenen Gamepads stand, und zwei von der App selbst gefahrenen. Das macht ihn wertvoll — bei den Ghosts ist die App der Fahrer, die Schreibpakete sind also die Ausgabe des Original-Reglers und nicht die eines Daumens. Erkennbar ist das sofort: die Ghost-Lenkung hat 119 bis 126 verschiedene Werte und nur 2,7–3,6 % Vollausschlag, während in den handgefahrenen Aufnahmen 196 von 235 Befehlen genau ±127 waren.

      Der Vorausblick: die nächsten drei Streckenteile

      In Bytes 16–18 schickt die App dem Auto die Typen der kommenden drei Kacheln, als Schiebefenster über das eingescannte Layout; das Fenster rückt bei jedem Kachelwechsel weiter. Im Leitplanken-Mitschnitt begannen diese Bytes auf die Millisekunde genau mit Bit 5 von Byte 14 (552 Pakete, beide Merkmale zugleich, in keinem anderen Mitschnitt vorhanden). Im Rennen umfasste der Vorausblick 11 verschiedene Fenster, deren kürzester erklärender Ring die Länge 11 hat — genau die 11 Module, die die App für „az2108“ angibt.

      Das Code-Alphabet ist vollständig

      0x02Geradebelegt

      0x03 war der letzte Unbekannte. Die gemeldete Codefolge lautete in allen 16 Runden identisch S R G R ? R, und über den Kachelzähler aufgelöst ist die Runde 11 Kacheln lang: S R2 G2 R3 L R2. Das einzelne 0x03 pro Runde sitzt genau dort, wo die einzelne Linkskurve liegt. (Die Strecke war als SR2G2R2LR2 notiert — die Daten zeigen an dieser Stelle drei Rechtskurven, nicht zwei.)

      Die Modus-Bytes für eigene Autos

      Bei beiden Ghosts konstant über 2496 bzw. 2457 Pakete: Byte 10 = 0x20 und Byte 15 mit Bit 3 (0x0c/0x0e). Das gesteuerte Auto bekam dagegen 0x60 und 0x04. Bit 1 von Byte 15 folgt dem Fahren und nicht dem Modus (Gas in 100 % der Pakete mit gesetztem Bit gegen 69,8 % ohne) und wird deshalb nicht nachgebildet. Korrektur: das früher hier genannte 0x30 war der Wert der handgefahrenen Leitplanken-Sitzung, nicht des Autonom-Modus.

      Berichtigung: Byte 15 Bit 3 ist kein Kantensignal

      Eine frühere Fassung dieser Karte behauptete, dieses Bit melde, dass das Auto am Bahnrand sei — also die lange gesuchte Querlage. Das war falsch. Drei Messungen widerlegen es: die Blockdauer ist praktisch konstant (Median 0,91 und 0,94 s, 10.–90. Perzentil 0,84–1,01 s), was ein Zeitglied ist und kein Kontakt; es gibt 17 Blöcke bei 16 Runden; und jeder einzelne beginnt auf Kachelindex 0 mit Code 0x01 (16 von 17 und 17 von 17). Es ist der Start/Ziel-Riegel, genau wie die Protokolltabelle weiter oben immer schon sagte.

      Die Korrelation mit dem nächsten Lenkbefehl der App (r = −0,40 und −0,32, der stärkste Wert aller 19 Meldebytes) war ein Ortsartefakt: der Riegel markiert immer dieselbe Stelle der Strecke, und dort lenkt die App eben konsistent. Wer nach Regelung sucht, muss den Ort herausrechnen — das ist die Lehre daraus.

      Es geht auch ohne Querlage — die App macht es vor

      GhostReststreuung der Lenkung je (Kachelindex, Phase)ohne Positionswissenerklärter Anteil
      0x20121,756,785 %
      0x20239,258,655 %

      Bei einem der beiden Ghosts sind 85 % der Lenkvarianz allein aus der Streckenposition erklärt. Die App fährt ihre autonomen Autos also weitgehend als Vorsteuerung aus Kachelindex und Phase innerhalb der Kachel — nicht aus einer Rückmeldung, denn sie hat genauso wenig eine wie wir. Im Rest steckt das gegenseitige Reagieren; der zweite Ghost mit 55 % war der stärker verwickelte.

      Das ist die Antwort auf „dann ist keine Ideallinie möglich?“ Möglich ist sie — als offene Bahnkurve über (Kachelindex, Phase), und genau so weit, wie die Original-App auch kommt. Was nicht möglich ist, ist nachzuweisen, dass das Auto die Linie einhält. Dafür bräuchte es zusätzliche Sensorik — eine Kamera von oben — und keine weitere Analyse des Funkverkehrs.

      Gegenprobe zum Ganzen: aus Kachelzähler und Start-Kachel rekonstruiert ergibt das Rennen 16 Runden je Ghost, nach der Anfangsphase stabil bei 7,07–7,31 s, die beiden Autos im Median 0,03 s auseinander — was zwei gleich eingestellte Ghosts auch tun sollten.

      Mehrspieler, Updates, offene Fragen

      Laut Hersteller können mehrere Spieler gleichzeitig fahren, jedes Handy über Bluetooth mit seinem eigenen Auto verbunden. Für die Renn-Organisation zwischen den Handys (Rundenzeiten, Startreihenfolge) wird vermutlich zusätzlich WLAN zwischen den Handys genutzt: zwei getrennte Funkwege, Bluetooth zum eigenen Auto und WLAN zu den anderen Handys.

      Das Auto kann seine Firmware auch per Bluetooth aktualisieren ("Over-the-Air-Update"), über ein Standardverfahren von Nordic Semiconductor.

      Noch nicht sicher bekannt: der genaue Streckensensor-Typ und die Bedeutung einiger Protokoll-Bytes (siehe die Tabellen weiter unten). Das Bremslicht ist seit dem 19.08.2026 entschlüsselt und wird angesteuert. Das Grundprinzip bleibt davon unberührt: Sensor liest Strecke, Funkchip verbindet Auto und Handy, Fahrphysik läuft im Auto.

      Software — das Fahrmodell

      Wer bestimmt das Fahrverhalten?

      Beide, aber an verschiedenen Stellen. Die App formt zuerst den Fahrerwunsch: Gänge, Drehmoment und eine simulierte Geschwindigkeit — und sendet dann das Ergebnis. Der entscheidende Punkt dabei: der Gaswert wird aus der simulierten Geschwindigkeit abgeleitet, nicht aus der Pedalstellung. Bekommt das Auto einen Vollgas-Wert, ist es fast sofort auf Höchsttempo; deshalb zieht es nur dann realistisch hoch, wenn die App den Wert über die Zeit hochrampt.

      Danach greifen noch drei Multiplikatoren an derselben Stelle: Geschwindigkeitsbegrenzung, Akku-Ausgleich sowie Tank und Schaden. Was das Auto aus dem fertigen Wert macht — wie es einlenkt, wie es Grip findet — entscheidet weiterhin seine eigene Firmware.

      Schaltet man die Physik in den Optionen ab, sendet die App wirklich nur noch die rohe Stickstellung. Dann ist sie die dumme Leitung, als die sie hier früher beschrieben war.

      Was ist echt gemessen, was rechnet die App?

      Echt aus dem Auto gemessen

      • Akkustand — Byte 10 (Schätzung, nicht kalibriert)
      • Teile-Zähler — Byte 11, erhöht sich bei jedem neuen Streckenteil
      • Typ des Streckenteils — Byte 12 (Start/Ziel, Gerade, Rechtskurve)
      • Off-Track-Flag — Byte 15
      • Rohe Bewegungswerte — Bytes 1 und 3, verrauscht, Bedeutung unbestätigt

      Nur in der App gerechnet

      • km/h, Drehzahl und Gangwahl — das Auto meldet keine Geschwindigkeit zurück
      • Lenkverhalten — Dämpfung, Expo-Kennlinie, Grip-Bonus beim Anbremsen
      • ABS, Tank, Schaden und die Crash-Erkennung (Schwellwert auf Bytes 1/3, deren Bedeutung unbestätigt ist)
      • Boxengasse — Tempolimit und Service, der mit der Standzeit wächst
      • Akku-Leistungsausgleich, Motorsound und alle Töne
      • Rundenzeiten — ausgelöst vom echten Byte 12, gestoppt aber im Gerät
      • Position auf der Minikarte — aus dem Teile-Zähler geschätzt (keine echte Ortung)

      Die Kennlinien des simulierten Antriebs

      Alle vier Bilder werden beim Öffnen dieses Tabs aus den aktuell eingestellten Werten berechnet — sie können also nicht von dem abweichen, was das Auto gerade tut.

      Das Drehmoment steigt spät an und erreicht sein Maximum erst bei rund 6200/min — typisch für einen hochdrehenden Saugmotor. Unten heraus zieht er deutlich schwächer.

      Radzugkraft je Gang. Jeder höhere Gang zieht schwächer, weil die Übersetzung kleiner wird — deshalb beschleunigt der 1. Gang brachial, endet aber schon bei rund einem Viertel der Höchstgeschwindigkeit. Als relativer Faktor beschriftet, nicht in Newton: das Modell kennt weder Masse noch Radradius, eine Newton-Achse wäre erfundene Physik.

      Dieselben Kurven abzüglich Roll- und Luftwiderstand — das ist die Beschleunigung, die tatsächlich übrig bleibt. Sie flacht nach oben hin ab. Die graue Linie ist der Verlauf ohne Gas.

      Der Anfahrtsverlauf, gezeichnet aus demselben Integrator, der auch den „0 → Vollgas"-Regler löst. Die rote Linie ist die Drehzahl: ihr Sägezahn sind die Schaltvorgänge, die man in den Hörbeispielen oben hört.

      Wie die Bremskraft gerechnet wird

      Die Verzögerung ist geschwindigkeitsabhängig, weil ein GT3 bei hohem Tempo durch Abtrieb deutlich stärker verzögert als kurz vor dem Stillstand:

      aBrems = (0,627 + 0,64 · v/vmax) · Bremspedal · Reibungskreis · Fahrbahn · Einfedern

      Die beiden Zahlen sind an eine reale GT3-Bremstabelle angepasst: 50 km/h in ~1,0 s, ansteigend auf 280 km/h in ~4,3 s. Nachgemessen 1,02 und 4,18 s — innerhalb von 3 %. Aus Höchstgeschwindigkeit bis Stillstand sind es 4,25 s.

      Berichtigung: hier stand früher, die Werte seien mit 1,5 % mittlerem Fehler an genau diese Tabelle angepasst, und der Bremsweg betrage 2,74 s. Beides passte nicht zusammen — 2,74 s aus Höchstgeschwindigkeit ist rund 57 % schneller als die 4,3 s der Tabelle. Nachgerechnet mit der blanken Formel und in der laufenden Schleife (die gleich rechnen, weil beim geraden Bremsen auf trockener Bahn jeder Multiplikator 1,0 ist): die alten 0,98/1,00 ergaben 0,64 und 2,75 s, eine spätere Abschwächung auf 0,784/0,80 ergab 0,80 und 3,44 s. Erst 0,627/0,64 treffen die Tabelle. Die Bremse ist damit schwächer als zuvor — in derselben Richtung, in die der Wunsch nach 80 % zeigte; der Regler Bremskraft (Standard 1,0) bleibt für den Geschmack.

      • Reibungskreis — ein Reifen kann seine Haftung nur einmal vergeben. Längs bleibt √(1 − quer²), also kostet Lenken beim Bremsen Verzögerung und umgekehrt.
      • Fahrbahn — eine 2×2-Matrix aus Wetter und Reifen: trocken auf Slicks 1,00, trocken auf Regenreifen 0,88, Regen auf Regenreifen 0,80, Regen auf Slicks 0,45.
      • Einfedern — die Radlast wandert beim Bremsen nach vorn. Wichtig ist die Normierung: der Faktor ist auf den eingefederten Zustand bezogen, nicht auf 50/50. Er kann also nur während des Einnickens Bremskraft wegnehmen, nie welche hinzuerfinden — sonst wäre die an echten Daten gefittete Verzögerung nicht mehr das, was sie verspricht.

      Die Radlastverlagerung hat zwei Zeitkonstanten: die Karosserie nickt in 80 ms ein, der Kraftaufbau am Reifen folgt in 450 ms. Genau diese Differenz erzeugt den kurzen Einlenkvorteil zu Beginn eines Bremsvorgangs. Gemessene Lenkwirkung bei vollem Einschlag, 170 km/h Anzeige, 2. Gang, trockene Bahn: Vollgas 0,76 · Ausrollen 1,02 · Bremse nach 45 ms 1,06 · nach 135 ms 1,18 · Dauerbremsung 0,46. Der Ausschlag nach oben und der tiefe Endwert sind dieselbe Ursache: die Karosserie ist schon vorn, der Reifen baut die Bremskraft aber erst auf — und sobald er sie aufgebaut hat, ist sie im Reibungskreis für das Lenken verbraucht.

      Geradeausfahren ohne Zustandswissen

      Das Auto meldet keine Ist-Geschwindigkeit. Es gibt kein Byte, aus dem hervorginge, wie schnell es gerade fährt. Das Gasbyte ist ein Sollwert, kein Regelkreis — es gibt keine Rückmeldung, gegen die geregelt werden könnte.

      Daraus folgt der zentrale Kunstgriff dieser App: das gesendete Byte wird aus der simulierten Geschwindigkeit abgeleitet, nicht aus der Pedalstellung. Würde man das Pedal direkt durchreichen, säße bei Vollgas sofort der volle Wert an und das Auto schießt los. Stattdessen läuft im Handy ein Fahrzeugmodell mit Motorkennlinie, Getriebe, Roll- und Luftwiderstand; dessen Geschwindigkeit wird auf den Bytebereich abgebildet. Das Auto bekommt also laufend den Wert, den ein echtes Fahrzeug in diesem Moment hätte.

      Zwei Feinheiten, die aus dem fehlenden Rückkanal folgen: erstens braucht ein stehendes Auto eine Mindestansteuerung (minMoveThrottle), um überhaupt loszubrechen — ohne sie wäre der erste Moment einer Beschleunigung zu schwach, um sich zu bewegen. Zweitens gibt es unterhalb von 10 km/h Anzeige kein Mittelding: entweder wird bewusst über der Losbrechschwelle gefahren, oder das Byte geht sauber auf 0. Dazwischen liegt genau der Bereich, in dem das Auto kriecht, stehenbleibt und wieder anruckt.

      Tankgewicht und Reifen

      Beide Modelle hängen an je einem Regler in den Optionen, dessen linkes Ende sie vollständig abschaltet — nicht „ein bisschen“, sondern rechnerisch exakt auf den Faktor 1, also auf das Verhalten ohne Simulation. Das ist Absicht: nur so lässt sich beurteilen, was das Modell überhaupt beiträgt.

      Tankgewicht

      Ein voller Tank ist totes Gewicht und kostet Beschleunigung und Bremsleistung gleichermaßen: Massefaktor = 1 + Regler · 0,30 · Füllstand. Bei vollem Regler und vollem Tank ist das Auto also 30 % träger; gemessener Bremsweg aus Höchstgeschwindigkeit 3,46 s statt 2,70 s.

      Wichtig für alle, die den Code weiterentwickeln: der Faktor wird auf die fertige Beschleunigung in update() angewandt, nicht innerhalb von thrustAt(). Die Startkalibrierung integriert durch thrustAt() und müsste sonst bei jedem Tankfüllstand neu gelöst werden. Die kalibrierte Zeit gilt damit für das leere Auto, und Sprit macht es langsamer — die ehrliche Richtung, denn erfinden darf ein Zusatzmodell nichts.

      Reifentemperatur

      Wärme entsteht aus der Arbeit, die die Reifen tatsächlich leisten: Querkraft plus Längskraft, beides nur solange das Auto rollt. Die Kühlung wächst mit dem Abstand zur Umgebungstemperatur, deshalb pendelt sich eine Temperatur ein statt davonzulaufen: T = 20 °C + 65 · (5,0/3,4) · Arbeit, Zeitkonstante etwa 19 s.

      Fahrweisebei 80 °C nachBeharrungstemperaturVerschleiß nach 10 min
      sanftnie49 °C — bleibt kalt33 %
      zügig48 s85 °C — Betriebsfenster74 %

      Dass sanftes Fahren die Betriebstemperatur gar nicht erreicht, ist kein Fehler, sondern genau der Zielkonflikt: wer schont, hat weniger Grip. Der erste Versuch mit anderen Raten lief bei ganz normalem Fahren auf 171 °C ein — dauerhaft im roten Bereich, was das Modell wie einen Defekt hätte aussehen lassen.

      Grip und Verschleiß

      Kalte Reifen rutschen, überhitzte rutschen, abgefahrene rutschen. Unterhalb des Betriebsfensters ist die Kennlinie quadratisch, damit die letzten Grad weniger zählen als die ersten. Gemessene Griffigkeit bei vollem Regler: kalt (20 °C) 0,65 · Betrieb (85 °C) 1,00 · überhitzt (110 °C) 0,70 · abgefahren 0,70.

      Der Verschleiß läuft mit derselben Arbeit und beschleunigt sich, sobald die Reifen heiß sind — ein harter Stint kostet also doppelt. Zurückgesetzt wird beim Boxenstopp und beim Rennstart, also genau dann, wenn ein echtes Auto auf neuen oder ausgekühlten Reifen losfährt. Der Grip wirkt auf Antrieb, Bremse und Lenkung.

      Auf dem Racing-Display zeigt der Reifenring die Temperatur: blau kalt, grün im Betriebsfenster, rot zu heiß. Bei abgeschaltetem Modell bleibt er grau und die Anzeige sagt „aus“ — eine Anzeige soll keine Simulation vortäuschen, die gar nicht läuft.

      Leerlauf, Schaltvorgang, Boxengasse

      Der Startzustand ist N. Der Antriebsstrang kennt drei Zustände — neutral, forward, reverse — und die Schaltkette ist R ← N ← 1 ← 2 … ← 6. N ist bei jeder Geschwindigkeit wählbar, weil Auskuppeln und Rollen normal ist; R nur im Stand.

      In N ist der gesendete Gaswert exakt 0 — nachgemessen — und die Drehzahl hängt nicht mehr an der Radgeschwindigkeit, sondern folgt dem Pedal mit einer Verzögerung von 0,22 s. Ein Motor ist kein Schalter.

      Eine Falle, die eigens abgefangen ist: im Automatikmodus muss N von selbst verlassen werden, sobald Gas kommt. Ohne diese Regel startet die App im Leerlauf und die Automatik käme nie heraus — dieselbe Fehlerklasse, die den Rückwärtsgang schon einmal unentrinnbar gemacht hat. Gemessen: Gang 1 kommt im ersten Sendetakt.

      Rückwärts ist doppelt gebremst: der simulierte Deckel liegt bei 11 % der Höchstgeschwindigkeit (gemessen 31 angezeigte km/h) und das gesendete Byte wird zusätzlich halbiert. R ist zum Rangieren da, nicht zum Fahren.

      Schaltgeräusch

      Selbst synthetisiert, keine Aufnahme. Ein pneumatischer GT3-Schaltvorgang ist nicht ein Geräusch, sondern drei innerhalb von etwa 80 ms, und das Ohr erkennt das Getriebe an ihrer Reihenfolge, nicht an der Klangfarbe: erst greift die Schaltklaue (harter, hoher Schlag mit unharmonischen Teiltönen), unmittelbar danach entlüftet der Steller (breitbandiges Zischen), und zuletzt nimmt der Antriebsstrang die Last auf (dumpfer Anteil um 128 Hz). Genau diese getrennte zeitliche Platzierung macht daraus einen Schaltvorgang statt eines allgemeinen Klickens.

      Hoch- und Runterschalten sind zwei verschiedene Dateien: beim Runterschalten muss der Steller gegen Motormoment halten, also ist der Luftauslass länger und alles sitzt tiefer. Fehlen die Dateien, springt ein Zweiklang ein — lieber ein Ersatz als Stille.

      Boxengasse

      Ein Zustandsautomat, zwei Wege hinein (Knopf oder Musterüberfahrt): off → limited → servicing → off. Der Knopf verlangt keinen Stillstand mehr, er schaltet den Limiter ein; das Anhalten löst den Service aus, das Losfahren beendet ihn. Der Limiter hält 80 angezeigte km/h (Faktor 0,2807), der Wert eines echten Boxengassen-Limiters.

      Zustand statt Schaden: der Balken startet voll und grün, jeder Crash nimmt ein Stück weg. Intern zählt damage weiter von 0 nach oben — nur die Darstellung ist gedreht, damit keine Crash-, Reparatur- oder Boxenstopp-Rechnung angefasst werden musste. Ein Balken, der wächst, während es schlechter wird, liest sich auf einen Blick falsch.

      Beim Notlauf steckte ein echter Fehler: leerer Tank und Totalschaden multiplizierten sich zu 0,0525, während die Losbrechschwelle bei 0,16 liegt. Das Auto fuhr dort nicht langsam, es zuckte — dieselbe Totzone wie beim Kriechen kurz vor dem Stillstand, nur an anderer Stelle. Der Notlauf hat jetzt eine Untergrenze statt nur Multiplikationen nach unten: gemessen 0,168.

      Streckengeometrie und Ideallinie

      Gemessene Maße: ein Streckenteil ist 25 cm breit und 43 cm lang; eine Gerade plus eine 60°-Rechtskurve nehmen zusammen 37×86 cm ein. Löst man den Fußabdruck nach dem Kurvenradius auf, ergibt sich 37 cm — das reproduziert 37,2×85,9 cm. Die Zeichenkonstanten sind daraus abgeleitet, nicht gewählt. Der zuvor per Hand gesetzte Radius von 34 Einheiten entspricht 36,5 cm und liefert 37,0×85,5 cm, war also bereits richtig; er steht jetzt in Zentimetern da, damit er nachprüfbar bleibt.

      Die Ideallinie entsteht durch Krümmungsglättung: jeder Punkt wandert wiederholt in Richtung der Mitte seiner Nachbarn, aber nur quer zur Fahrtrichtung, und wird nach jedem Durchlauf auf die Fahrbahn geklemmt. Sie kann die Bahn also nicht verlassen — nachgemessen: größte Abweichung 9,3 cm bei 12,5 cm Halbbreite.

      Ein Abbruchkriterium über die Schrittweite war hier falsch, und die Messung zeigte es: bei 14 Abtastpunkten je Teil liegen die Nachbarn 2,9 Einheiten auseinander, die Mitte liegt fast auf dem Punkt selbst, und ein Durchlauf verschiebt um Bruchteile eines Millimeters. Eine 0,5-mm-Schwelle meldete deshalb nach einer Iteration Konvergenz — und die fertige „Ideallinie“ nutzte 1,1 cm einer 25 cm breiten Bahn, war also die Mittellinie mit einer Delle. Der Versatz baut sich erst über viele Durchläufe auf, also wird eine feste Anzahl gerechnet, und ausgegeben wird nicht ein Restwert, sondern wie viel Versatz die Linie tatsächlich nutzt — die Zahl, an der man sieht, ob die Rechnung etwas getan hat.

      Was die Linie nicht ist: eine Vorgabe, deren Einhaltung die App prüfen kann. Kein Byte meldet die Querlage des Autos. Die Linie sagt, wo gefahren werden sollte; ob es geschieht, weiß niemand.

      Der Streckencode (z. B. SG2R3G2R3B@90) ist ein Buchstabe je Element mit Wiederholungszahl, dazu die Ausrichtung: S Start, G Gerade, R rechts, L links, B Boxengasse. Absichtlich kein Base64 — einen Code, den man nicht lesen kann, kann man auch nicht prüfen.

      Audio

      Wie der simulierte Antrieb klingt

      Ein kompletter Fahrzyklus: Anlasser, Leerlauf, Vollgas-Start durch alle sechs Gänge, dann Anbremsen mit fünf Rückschaltungen und zurück in den Leerlauf — rund 10 Sekunden. Beim Hochschalten fällt die Drehzahl, beim Runterschalten springt sie hoch, weil der kürzere Gang den Motor bei gleicher Geschwindigkeit schneller dreht. Das kurze Bellen dabei ist Zwischengas: echte GT3-Getriebe gleichen die Drehzahl beim Runterschalten an.

      Porsche — Boxer-6, gleichmäßig zündend

      BMW — Reihen-6, Turbo

      Mustang — V8, Cross-Plane

      Die übrigen Effekte

      Bremse — tonal, ACC-Charakter

      Crash — 2 von 4 Varianten

      Boxenstopp — Schlagschrauber

      Motorstart — nur der Startvorgang

      Porsche, BMW und Mustang sowie alle Effekte oben sind vollständig synthetisch — Zündimpulse, gefaltet mit der Resonanz des Auspuffkrümmers, nach dem Vorbild von ange-yaghi/engine-sim (MIT). Der Unterschied zwischen den Fahrzeugen kommt nicht aus der Tonhöhe, sondern aus den Zündabständen: die beiden Sechszylinder zünden gleichmäßig alle 120°, der Cross-Plane-V8 dagegen ungleichmäßig innerhalb jeder Bank — daher das Blubbern. Der Crash ist bewusst dumpf gehalten: ein GT3-Kontakt ist Carbon, das den Stoß schluckt, kein splitterndes Glas.

      Nicht jeder Klang in der App ist das. Der Corvette-Motor und die Strecken-Ambience sind aus lizenzfreien Pixabay-Aufnahmen geschnitten, nicht gerechnet — die Pixabay-Lizenz erlaubt das, und es gab keinen Grund, nachzubauen, was eine gute Aufnahme schon liefert. Die unbearbeiteten Quelldateien sind nicht Teil des Repos, nur die geschnittenen Ableitungen. Vollständige Aufschlüsselung, Datei für Datei: audio/CREDITS.md.

      Audio-Engine

      Die drei Hauptmotoren sind vollständig synthetisch — es wird keine Aufnahme wiedergegeben. Modelliert nach dem Ansatz von ange-yaghi/engine-sim (MIT-Lizenz):

      • Zündereignisse statt Klangfarbe: pro Arbeitstakt ein Druckimpuls. Beim V8 mit ebener Kurbelwelle zünden die Bänke ungleichmäßig — daraus entsteht das typische Blubbern von selbst, es wird nicht nachgebaut.
      • Faltung mit einer Auspuff-Impulsantwort. Die Faltung ist zyklisch gerechnet, damit die Schleife am Ende exakt wieder auf den Anfang passt.
      • Ventiltriebgeräusch im Nockenwellentakt, mit Streuung in Zeit und Stärke, plus weiche Sättigung und Fehlzündungen im Schiebebetrieb.

      In der App laufen drei Schleifen (Leerlauf, Mitte, hoch) gleichzeitig und werden überblendet; die Tonhöhe kommt aus playbackRate, die Gewichte summieren sich exakt auf 1, damit die Lautstärke beim Überblenden nicht atmet.

      Corvette C6, Strecken-Ambience, Regen und Donner sind dagegen aus lizenzfreien Pixabay-Aufnahmen geschnitten. Welche Datei woher stammt, steht in audio/CREDITS.md.

      Mustererkennung: Paketvarianten testen

      In sieben aufgezeichneten Fahrten hat das Auto keinen einzigen Streckencode gemeldet, während der Mitschnitt der Original-App voll davon ist. Das Schreibpaket im Moment des ersten Codes dort ist byteweise die Form, die wir senden — im Dauerbetrieb unterscheidet uns also nichts. Was die Original-App aber zusätzlich gesendet hat und wir nie:

      keine Variante aktiv

      So testen: Variante wählen, dann langsam über ein Muster fahren — Start/Ziel, ein Streckenteil oder den Boxengassen-Ausdruck. Die Anzeige zählt, ob Byte 12 den Wert 0xff verlässt. Sobald irgendwo eine Zahl größer null steht, ist die Ursache gefunden. Jede Variante behält eine gültige Prüfsumme, ein Fehlschlag ist also ein echtes Ergebnis und kein verworfenes Paket.

      Telemetrie aufzeichnen

      Zeichnet jedes Paket in beiden Richtungen auf — was das Auto meldet und was die App sendet — mit Zeitstempel, und exportiert es als CSV. Damit ist kein btsnoop nötig: die Datei ist bereits beschriftet und entschlüsselt.

      Protokoll-Labor (NUS RX/TX)

      Schreibt frei konfigurierbare Byte-Pakete an NUS RX (6e400002) und zeigt gleichzeitig alle Notify-Werte von NUS TX (6e400003) an — damit du live sehen kannst, was das Auto zurückmeldet, während du Kombinationen ausprobierst.

      Bekannt (aus einer unabhängigen Reverse-Engineering-Runde zum selben Auto, per BLE-Sniffer ermittelt): echte Kommando-Pakete sind 20 Byte lang (2 Byte Präfix + 17 Datenbytes + 1 Prüfsumme), gesendet alle ~45ms. Byte-Offset 6 = Gas/Bremse (0xDF=Leerlauf, größer=Gas, kleiner=Bremse). Die Prüfsumme ist noch nicht geknackt — deshalb unten zuerst das echte, garantiert gültige Leerlauf-Paket laden und unverändert wiederholt senden (reproduziert dieselbe gültige Prüfsumme, ohne sie berechnen zu müssen).

      Streckeneditor

      bereit
      Im Vollbild: D-Pad wählt, X baut, O rückgängig, Dreieck Reset, Quadrat dreht 90°

      Schwarz ist die Fahrbahn, weiße Striche trennen die Streckenteile. Randsteine in Fahrtrichtung: links rot-weiß, rechts blau-weiß — die Boxengasse liegt deshalb rechts. Ihre Breite ist 9,5 % der Fahrbahnbreite, ausgemessen aus den Streckenkarten der Original-App. Die dünne farbige Linie ist die berechnete Ideallinie — krümmungsärmster Verlauf innerhalb der Fahrbahn. Ihre Farbe zeigt, ob dort gebremst würde: grün am Gas, rot beim Bremsen, mit fließendem Übergang. Gebremst wird dort, wo die Krümmung voraus ansteigt — eine Kurve, die schon mit festem Radius gefahren wird, braucht keine Bremse mehr. Beides ist eine Rechnung, keine Messung: dass ein Auto die Linie einhält, kann die App nicht prüfen, weil kein Byte die Querlage meldet.

      Der Code beschreibt die Reihenfolge der Teile und die Ausrichtung. Damit stellst du auf einem anderen Gerät dieselbe Strecke ein, ohne sie neu zu klicken.

        Druckvorlagen

        Muster zum Ausdrucken und Auslegen. Wichtig beim Drucken: A4 quer, Skalierung 100 % / „Tatsächliche Größe" — auf keinen Fall „an Seite anpassen", sonst stimmen die Balkenabstände nicht mehr und der Sensor liest gar nichts. Der Pfeil zeigt in die Fahrtrichtung.

        Start / Ziel

        Zählt Runden und löst im Rennmodus die Rundenzeit aus. Erwarteter Code 0x01. Rekonstruktion aus einem Foto — wenn du das Original-PDF hast, nimm lieber das.

        Boxengasse

        Löst Tempolimit und Boxenstopp aus. Welchen Code das Auto dafür meldet, ist unbestätigt — nach dem Drucken einmal überfahren und unten mit der Muster-Sonde ablesen.

        Boxengasse

        Fährt das Auto über das Boxen-Muster, greift ein Tempolimit von 40 %. Bleibt es dann stehen, läuft der Service — je länger du stehst, desto mehr Sprit und Reparatur. Beim Losfahren ist das Limit wieder weg.

        Zuletzt überfahrenes Muster: -

        Muster-Sonde: fahr über ein beliebiges ausgedrucktes Muster — hier steht sofort, welchen Code das Auto meldet. Sicher bekannt sind 0x01 Start/Ziel, 0x02 Gerade, 0x03 Linkskurve und 0x04 Rechtskurve; alles andere ist unbestätigt. Trag hier den Code ein, den dein gedrucktes Boxen-Muster tatsächlich auslöst — 0x08 war nie ein reales Signal und ist deshalb nicht mehr die Vorgabe.
